# Voting workflow and permissions (2026-11-06)

- Invitations open the sticker calendar before login. Guest selections stay in sessionStorage, scoped to the meeting, for at most 24 hours. They are not shared until login and a successful save. New meeting creators can also select stickers in a local preview before login. OAuth cancellation/failure keeps the draft.
- Kakao's existing name supplies the initial nickname; it can be edited in the participation bar. The nickname step no longer blocks first voting.
- Creating, joining, editing metadata, confirming, cancelling, and deleting run through the signed-session server API. Legacy meeting ownership is verified using the original deterministic ID and immutable original title. Metadata and reservations have no client write grant.
- Firebase custom tokens contain a server-generated profileKey claim. A profile is only readable/writable by the matching signed account. Calendar/admin configuration, reservations, migration backups, leases and jobs remain server-only. Browser votes are restricted to the authenticated member, valid dates in the candidate period, valid slots and values, and unconfirmed polls.
- The owner can edit expected count from the participation card. It must be an integer between 2 and 100, and cannot be below the number of joined members.
- The owner can confirm a lunch/dinner candidate from the ranking or the top action, change that confirmation, cancel it, and share its link. Confirmation freezes sticker editing until cancellation.
- Per the product decision, ALL current participants plus the owner get a reservation. Other polls use an automatic X on the same date AND same lunch/dinner slot. Raw manual choices are retained separately. Cancellation/change restores the original choice; a second overlapping reservation keeps X in place. Google Calendar remains read-only; no Google event is created.
- A durable outbox propagates X in batches below the Workers Free 50 external-fetch limit. The confirming browser drains the queue immediately. A five-minute cron resumes interrupted jobs. A reservation is also reconciled whenever a member joins another poll or its period changes. Batches and their progress are atomically committed. A server-only lease serializes competing metadata and propagation writes.
- The bundled database policy is installed automatically by the backend once per schema version, using the existing service account. The previous rules are retained at private `policyBackups/workflow-v2`; successful installation is marked at private `schema/workflow-v2`. No request can supply arbitrary rules. Existing profiles, meeting IDs, links and raw stickers are retained.

Validation: Node workflow and regression suites; 70-target interrupted propagation, overlapping reservations, restoration of manual choices, owner denial, valid dates, participant count limits, policy backup/retry, guest expiry; native mobile Chromium fixture verifies guest interaction, login draft save, read-only confirmation, owner controls and layout. The fixture uses isolated demo data, not production writes. Actual Kakao/Google account consent is not automated.
